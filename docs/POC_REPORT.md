# PoC report

Status of the proof of concept against its exit criteria, with what the data does and does not support.
Raw outputs: `eval/results/` (`temporal_*.md|jsonl`, `experience_*.md|jsonl`, `n1/`, `n2/`).

## Setup (applies to everything below)

- One LLM (Gemini 2.5 Flash, temperature 0) plays every role: extraction, query analysis, answering, planning, reflection.
  Embeddings: `gemini-embedding-001`. Systems differ only in what memory they provide; prompt and answer schema are shared.
- Benchmarks are **synthetic**, generated by this repo (`eval/scenarios.py`, `eval/simulator.py`), with ground truth by
  construction. Nothing here shows real-enterprise performance.
- Seed 0 of the temporal world was used for development (it drove the entity-resolution fixes). Reported temporal numbers
  use held-out seeds 1-3. Seeds 1-3 of the experience task drove the lesson-verification fix, so the reported experience
  numbers use fresh seeds 4-8.
- Grading is programmatic on the answer's structured `values`; no LLM judge.

## Experiment 1: temporal facts, contradictions, poisoning (seeds 1-3, 147 questions per system)

| Metric | A none | B last-10 docs | BF all docs | C vector RAG | **Full memory** |
|---|---|---|---|---|---|
| Current fact | 0% | 55% | 100% | 58% | **100%** |
| Historical (as-of, before) | 0% | 45% | 100% | 100% | **100%** |
| Change date | 0% | 63% | 100% | 100% | **100%** |
| Multi-valued recall | 0% | 0% | 100% | 100% | **100%** |
| Poisoning / stale claim | 0% | 0% | 8% | 0% | **42%** (n=12) |
| Alias variants | 0% | 44% | 100% | 92% | **100%** |
| Out-of-order ingestion | 0% | 25% | 100% | 75% | **100%** |
| **All** | 0% | 42% | 93% (87-96) | 82% (75-88) | **95% (90-98)** |
| Stale/poisoned answer rate (lower better) | 0% | 8% | 16% | 43% | 14% |
| Avg context chars | 0 | 1.6k | 9.1k | 0.75k | 2.3k |
| LLM calls (ingest + answer) | 147 | 147 | 147 | 147 | 476 |

Full minus vector RAG: **+12.9 points, 95% bootstrap CI [+8.2, +18.4]**.

What this supports:
- Structured, temporal, authority-aware memory clearly beats vector RAG on the same documents, mainly on current-fact
  questions (100% vs 58%): RAG surfaces outdated or unverified documents and the LLM trusts them.
- Poisoned or stale low-authority claims never overwrote accepted facts. Every injected claim was stored as `conflicted`
  and sent to review (4 pending reviews in the last seed, all intended), and history stayed intact.

What it does not support:
- **No advantage over simply putting all documents in context** (95% vs 93%, within noise). The world is only ~60
  documents (about 9k characters), so the long-context baseline is unrealistically strong. The design's case rests on
  scale (thousands of documents, many sessions), which this PoC did not test.
- The "poisoning 42%" figure is a strict-grading artifact: in all 4 misses the answer correctly named the accepted value and
  *also* said a disputed claim exists (for example "Oracle ... however, there is a conflicting claim that it uses
  PostgreSQL"), so the disputed value appears in `values`. Reading these as correct would give 100%, but the grader was not
  changed after seeing results. A separate `disputed_values` field in the answer schema would fix this properly.
- Cost: 3.2x more LLM calls than the baselines (ingestion extraction dominates).

## Experiment 2: repeated mistakes (fresh seeds 4-8, 5 x 30 tasks)

| System | Success rate | Repeated Mistake Rate (lower better) |
|---|---|---|
| A no memory | 66% (58-73) | 42% (33-52), n=97 |
| B history (last 8 episodes) | **91%** (86-95) | **18%** (10-31), n=49 |
| C episodic RAG (top-4) | 89% (83-93) | 23% (14-35), n=57 |
| Full experience memory | 77% (70-83) | 24% (16-33), n=97 |

Full-system success by task block (8 tasks each, last block shorter): 65%, 78%, 80%, 90%.

Sensitivity to min evidence for promotion (Full only, same seeds): N=1 72%, N=2 73%, N=3 (default) 77%.

Conclusions:
- Experience memory beats no memory and improves over the run (65% to 90%), but **loses to plain conversation history and
  episodic retrieval**. The exit criterion "repeated-mistake rate lower than Baseline B" is **not met**.
- Lowering the evidence threshold did not help, so waiting for 3 failures is not the explanation. Candidate causes, not yet
  tested: history shows the LLM the concrete failing plan and the error text, which is more informative than a one-line
  lesson; lessons are only injected into about 40% of tasks; lesson quality and retrieval of the right lesson.
- RMR is confounded across systems: a system that fails less has fewer "opportunities" (different denominators). Success
  rate is the cleaner comparison.
- Two real bugs found and fixed along the way: the lesson writer inverted a step ordering (fixed by contrast episodes plus a
  verification pass, with unverified lessons kept as non-injected hypotheses), and failures after a lesson was applied were
  double counted as supporting evidence.

## Exit criteria

| Criterion | Result |
|---|---|
| Full beats vector-only on current-fact accuracy and stale-answer rate (temporal) | Met (held-out; 100% vs 58%, 14% vs 43%) |
| Poisoning detected, history preserved | Met for detection and history; strict answer grading shows 42% (see above) |
| Repeated-mistake rate lower than Baseline B | **Not met** (24% vs 18%; success 77% vs 91%) |
| All unit tests pass offline with the fake LLM | Met (30 tests) |

## Bugs the evaluation found in the implementation (worth remembering)

1. Entity resolution flagged distinct names sharing a suffix (`BillingService` vs `SubscriptionService`) as ambiguous, sending
   about half of all facts to review. Fixed by comparing the distinctive name core and requiring string similarity 0.75 for
   embedding matches (distinct pairs measured at 0.50-0.62, true variants at 0.82+).
2. Failure-class attribution used a 0.6 embedding threshold; unrelated names measure 0.55-0.69 and same-cause names
   0.80-0.92. Now 0.78.

## Implications for the design and the MVP

1. Keep entity resolution and conflict rules as designed, with the measured thresholds (now in `config.py`).
2. Add to design section 19: lessons must be verified against evidence before injection; counter-example failures are not evidence.
3. Before investing in MVP infrastructure, run the **scale experiment** (design section 35): grow the world to thousands of
   documents so that context stuffing and vector RAG degrade, and see whether structured memory holds. That is where the
   claimed advantage should show.
4. Rethink experience memory: test injecting raw failed episodes alongside distilled lessons, and diagnose why lessons
   underperform raw history, before building the mining pipeline for production.
5. Answer schema: add `disputed_values` so conflicts are machine-readable.
6. MVP items from the plan stand (Postgres + pgvector, FastAPI, async write path, connectors, ACLs, observability, UI).
